# netscan

Мониторинг сети на проде. Раз в минуту проверяет потери и задержку, раз в полчаса снимает короткую скорость. По этим файлам видно, проседает ли канал, и можно идти к провайдеру с цифрами.

Нужны Docker и [Task](https://taskfile.dev).

```bash
task deploy:up
task deploy:health
task deploy:logs
task deploy:down
```

Первый `deploy:up` копирует `deploy/.env.example` в `deploy/.env`. Контейнер в host network: мерит аплинк сервера, а не docker-мост. Health на самом хосте: `http://127.0.0.1:19090/health`.

## Данные

Лежат в volume, каталог внутри контейнера `/data`. Старше суток удаляются.

- `probes.csv` — каждую минуту. Шлюз и `1.1.1.1`, `8.8.8.8`, `9.9.9.9`: потери, RTT, джиттер, TCP на `:443`, ошибки и drops интерфейса, сколько байт ушло за минуту.
- `speed.csv` — раз в 30 минут, не дольше 8 секунд и не больше 32 МиБ. Если тест занял все 8 секунд, канал был около 32 Мбит/с или медленнее.
- `incidents/` — отчёт `mtr`, когда потери от 1% или задержка сильно выше обычной за последний час. Не чаще одного раза в 10 минут.

`during_speedtest=1` в `probes.csv` — минута, в которую шёл замер скорости. Эти строки в претензию не класть.

Шлюз плохой, внешние адреса нормальные — проблема на сервере или до провайдера (кабель, порт, роутер). Шлюз чистый, а плохо до всех внешних сразу — смотреть `mtr`: там видно, с какого хопа началось.

Настройки в `deploy/.env`: цели, интервалы, пороги.

Свой образ:

```bash
NETSCAN_IMAGE=user/netscan:latest task image:build:push
```

На сервере без сборки: прописать тот же `NETSCAN_IMAGE` в `deploy/.env.hub` и запустить `task hub:up`.
